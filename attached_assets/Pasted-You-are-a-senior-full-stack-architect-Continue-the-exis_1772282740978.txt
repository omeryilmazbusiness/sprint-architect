DOMAIN REQUIREMENTS (must implement in Sprint 2):
A) Roles
- ADMIN: can access all clinics, manage clinics/managers (basic endpoints only if needed)
- MANAGER: belongs to exactly one clinic (clinicId non-null) and MUST be clinic-scoped
- PATIENT: logs in via patientKey + deviceId (no email/password)

B) Multi-tenant / Clinic scoping (CRITICAL)
- Every clinic-owned resource will be tied to clinicId.
- For all MANAGER requests, clinicId MUST be enforced centrally (middleware/guard), not by manual filtering in each handler.
- The application layer should receive an “Actor/Context” object that includes role, userId, clinicId (if any).
- Repositories for clinic-owned entities must require clinicId in their query methods to avoid accidental cross-tenant access.

C) Auth flows
1) Admin/Manager login:
- Endpoint: POST /v1/auth/login
  Input: { email, password }
  Output: { accessToken, refreshToken, user: {id, role, clinicId?} }
- Endpoint: POST /v1/auth/refresh
  Input: { refreshToken }
  Output: new { accessToken, refreshToken }
- Endpoint: POST /v1/auth/logout
  Input: { refreshToken } OR use token revocation strategy
  Output: 204

2) Patient login (fast):
- Manager creates patient (not in this sprint unless needed; at minimum implement DB model and login).
- Patient has unique patientKey (random, non-guessable).
- Endpoint: POST /v1/patient/auth/login
  Input: { patientKey, deviceId }
  Rules:
   - If patient has no active device bound -> bind deviceId and allow login.
   - If patient has active bound deviceId equal to input -> allow login.
   - If patient has active bound deviceId different -> deny with clear error code DEVICE_ALREADY_BOUND.
- Endpoint: POST /v1/patient/:id/reset-device
  Allowed: ADMIN or MANAGER of same clinic
  Action: revoke existing device binding so patient can bind a new device.
- Patient tokens should result in actor role PATIENT, with patientId + clinicId in token context.

D) Token strategy
- JWT access token short TTL (e.g., 15m)
- Refresh token long TTL (e.g., 30d)
- Store refresh tokens in DB with rotation:
  - refresh_tokens table: id, userId nullable, patientId nullable, tokenHash, expiresAt, revokedAt, createdAt
- On refresh: rotate refresh token (invalidate old, create new).
- On logout: revoke refresh token.

E) Database schema changes (Prisma)
Add tables/models:
- patients: id, clinicId, fullName, arrivalDate nullable, departureDate nullable, patientKey unique, status, createdAt
- devices: id, patientId unique (or 1 active binding rule), deviceId, boundAt, revokedAt nullable
- refresh_tokens: id, userId nullable, patientId nullable, tokenHash, expiresAt, revokedAt, createdAt
