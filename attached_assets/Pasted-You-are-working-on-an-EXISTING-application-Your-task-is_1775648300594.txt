BUSINESS RULE
When a new guest is created, that guest receives a guest key.

That guest key must work like this:

1. The first successful login with that guest key determines the ONLY allowed device
2. The deviceId of that first successful login must be captured and bound to that guest
3. After that, the same guest key must work ONLY on that same device
4. Any different device attempting to use the same guest key must be rejected
5. The lock must be enforced by backend/domain logic, not only by frontend logic
6. The system must be production-ready, secure, maintainable, and auditable

STRICT REQUIREMENT
This is NOT a UI-only restriction.
This is NOT a frontend-only check.
This is a real system-level device lock.

PRIMARY GOAL
Build a professional one-device-per-guest authentication model where:
- first successful device becomes the trusted device
- same guest key cannot be used on another phone/tablet/device
- only authorized reset can unlock/rebind the guest to a new device

REQUIRED BUSINESS LOGIC

A. GUEST CREATION
When a new guest is created:
- a guest key must be generated
- the guest starts with NO bound device yet
- device binding should not be prefilled
- device lock is created only on FIRST successful login

B. FIRST SUCCESSFUL GUEST LOGIN
When a guest uses the key for the first time:
- validate the guest key
- retrieve the deviceId from the app/client
- if there is no active bound device yet:
  - bind this deviceId to the guest
  - record firstBoundAt
  - allow login
  - issue tokens/session only AFTER binding succeeds

C. REPEAT LOGIN ON SAME DEVICE
If the same guest returns on the same device:
- validate guest key
- compare deviceId with stored active deviceId
- if match:
  - allow login
  - update lastSeenAt if appropriate
  - issue/refresh session safely

D. LOGIN ATTEMPT ON A DIFFERENT DEVICE
If a different device uses the same guest key:
- reject login
- do NOT overwrite the old bound device
- do NOT issue tokens
- return a clear business error

E. RESET / REBIND FLOW
Only an authorized role (manager/admin) may reset the binding:
- revoke the current active binding
- invalidate active refresh/session tokens as needed
- next successful guest login can bind a new device
- audit log this event

You must ensure:
