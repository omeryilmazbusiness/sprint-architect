Rules:

1) Users list endpoint (already exists but ensure stable DTO):
GET /v1/admin/users?clinicId=&entityType=&status=&search=&page=&pageSize=
Return items with:
{
  id,
  entityType: "ADMIN"|"MANAGER"|"PATIENT",
  displayName,
  clinicId,
  clinicName,
  role,
  status,
  email?,
  phoneE164?,
  createdAt
}
Pagination: totalCount, page, pageSize

2) Bulk deactivate endpoint (NEW):
POST /v1/admin/users/bulk-deactivate
Body (zod):
{
  userIds: string[],      // managers/admins
  patientIds?: string[]   // if entityType PATIENT is separate table
}
Or better unified:
{
  targets: [
    { id: string, entityType: "ADMIN"|"MANAGER"|"PATIENT" }
  ]
}
Behavior:
- Validate all IDs exist.
- Do not allow deactivating currently logged-in admin.
- If a MANAGER is the clinic.primaryManagerUserId:
  - Either block with error code PRIMARY_MANAGER_DELETE_BLOCKED
  - Or require parameter force=false by default and return a list of blocked ids.
Recommended: block and return blocked list.

Effect:
- For ADMIN/MANAGER: set users.status = INACTIVE and statusReason="ADMIN_DEACTIVATED"
- For PATIENT: set patients.status = INACTIVE (or a dedicated field) and statusReason="ADMIN_DEACTIVATED"
- Add audit log entry: ADMIN_BULK_DEACTIVATE with metadata (counts, ids)

Return:
{
  deactivated: number,
  blocked: [{id, reason}],
}

3) Optional single deactivate endpoint (not required if bulk covers it)
DELETE /v1/admin/users/:id -> internally calls same usecase.
