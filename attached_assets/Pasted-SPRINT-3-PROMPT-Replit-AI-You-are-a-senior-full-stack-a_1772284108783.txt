B) Key business rules
- Patient creation generates a non-guessable unique patientKey (crypto random). Ensure uniqueness (retry on conflict).
- Manager can only access patients/doctors/hotels/transports belonging to their clinic.
- Assignments must validate clinic ownership: you cannot assign a hotel/transport from another clinic.
- Appointment dates: startAt required; endAt optional but if provided must be >= startAt.
- Documents: Manager assigns document types to patient; patient upload will be in future sprint, but now the assignment and listing must exist.

C) API Endpoints (versioned: /v1)
Implement these endpoints in interfaces layer with zod validation and proper RBAC:

ADMIN (minimal – only if needed for verification)
- GET /v1/admin/clinics/:id/summary  (optional): counts of patients, doctors, upcoming appointments (for later dashboards)

MANAGER – Clinic scoped
Patients:
- POST   /v1/manager/patients
- GET    /v1/manager/patients?search=&page=&pageSize=
- GET    /v1/manager/patients/:id
- PUT    /v1/manager/patients/:id
- DELETE /v1/manager/patients/:id  (soft delete recommended: status=INACTIVE)

Doctors:
- POST/GET/GET:id/PUT/DELETE  /v1/manager/doctors...

Hotels:
- POST/GET/GET:id/PUT/DELETE  /v1/manager/hotels...

Transports:
- POST/GET/GET:id/PUT/DELETE  /v1/manager/transports...

Assignments:
- PUT /v1/manager/patients/:id/assign-hotel       body: { hotelId, stayDays, roomNo, checkInDate, checkOutDate }
- PUT /v1/manager/patients/:id/assign-transport   body: { transportId }
- POST /v1/manager/patients/:id/assign-documents  body: { documentTypeIds: string[] } (idempotent; avoid duplicates)

Appointments:
- POST   /v1/manager/patients/:id/appointments
- GET    /v1/manager/patients/:id/appointments?from=&to=
- PUT    /v1/manager/appointments/:appointmentId
- DELETE /v1/manager/appointments/:appointmentId (or status=CANCELLED)

  appointments: [ ... ],

}
Note: PATIENT role must be clinic-scoped too via token context.
